## Question

1. 두 스레드가 락 없이 공유 변수를 각각 100만 번 1씩 늘리면 결과는 200만이 되는가?
2. 같은 코드인데 실행할 때마다 결과가 다르다면, 무엇이 결과를 바꾸는가?
3. `volatile`은 이 문제를 해결하는가?

## Hypothesis

- 락이 없으면 `balance = balance + 1`이 읽기·더하기·쓰기로 쪼개져 있어서, 두 스레드가 엇갈리며 서로의 결과를 덮어쓴다. 그래서 200만보다 작게 나온다.
- `volatile`은 값을 매번 메모리에 반영할 뿐 읽기·더하기·쓰기를 한 덩어리로 만들지 않으므로, 여전히 손실이 난다.
- 락(`ReentrantLock`, `synchronized`)은 항상 정확히 200만이 나온다.

## Experiment

`RaceCondition.java` 하나로 모드를 바꿔 가며 실행했다. 회차마다 `balance`를 0으로 초기화하고 스레드 두 개를 새로 만든다.

| 모드 | 증가 코드 |
|---|---|
| `none` | 일반 `static int`, 락 없음 |
| `volatile` | `static volatile int`, 락 없음 |
| `lock` | `ReentrantLock` + `try/finally` |
| `sync` | `synchronized (monitor)` |

- 두 번째 인자 `latch`를 주면 `CountDownLatch`로 두 스레드를 동시에 출발시킨다.
- 실행한 조합

|---|---|---|---|

## What I learned

### 1. 원자성은 요청해야 생긴다
`balance = balance + 1`은 바이트코드에서 `getstatic` → `iconst_1` → `iadd` → `putstatic`으로 쪼개진다. 기계어 명령 하나로 합쳐져도 CPU 안에서는 읽기·더하기·쓰기로 실행되고, 멀티코어에서는 그 사이에 다른 코어가 끼어들 수 있다. 원자성은 락이나 원자 클래스로 명시적으로 요청해야 하고, 맨 아래에서는 x86의 `lock` 접두어 명령이 캐시 줄을 독점한 채 읽기~쓰기를 끝내는 방식으로 지켜진다.

### 2. 덮어쓰기 한 번이 증가 수십만 번을 지울 수 있다
스레드 1이 값을 읽은 직후 운영체제에 의해 오래 멈춰 있는 동안 스레드 2가 수만 번 증가시키면, 스레드 1이 깨어나 옛 값 + 1을 쓰는 순간 그 증가가 한꺼번에 사라진다. B에서 결과가 100만보다 작게 나온 이유다.

### 3. JIT가 경쟁 상태를 숨겼다 (A와 B의 차이)
A와 B는 같은 코드인데 결과가 달랐다. 차이는 JIT 컴파일 여부다.
- JVM은 처음에 인터프리터로 실행하다가, 반복문이 많이 돌면 실행 도중에 기계어로 컴파일된 코드로 전환한다(OSR). A의 1~3회차는 아직 인터프리터이거나 전환 중이라 손실이 났고, 손실이 점점 줄었다.
- JIT는 "단일 스레드 기준으로 결과가 같으면" 코드를 바꿀 수 있다. 반복문 안에 락이나 `volatile`이 없으므로, `balance`를 레지스터에 두고 처음에 한 번 읽고 마지막에 한 번 쓰는 형태로 바꿀 수 있다.
- 그러면 스레드 하나의 작업이 거의 0ms에 끝나 두 스레드가 겹칠 시간이 사라진다. 그래서 A의 4회차 이후는 대부분 정답이었다.
- 두 스레드가 정말 동시에 출발하면 둘 다 같은 시작값을 읽고 둘 다 같은 최종값을 써서, 한쪽 몫이 통째로 사라진다. 정확히 1,000,000 손실이 그 흔적이다.
- **결론: 정답이 나왔다고 스레드에 안전한 것이 아니다. 버그는 그대로이고, 최적화로 틈이 짧아져 숨었을 뿐이다.**

### 4. `volatile`은 가시성만 주고 원자성은 주지 않는다
`volatile`은 매번 메모리에서 읽고 메모리에 쓰도록 강제해서, JIT가 반복문을 한 번 읽고 한 번 쓰는 형태로 바꾸지 못한다. 그래서 C는 인터프리터로 돈 B와 비슷하게 매 회차 손실이 났다. 읽기·더하기·쓰기 사이의 틈은 막지 못한다. 역설적으로 `volatile`을 붙이자 숨어 있던 버그가 항상 드러났다.

### 5. 락만 매번 정답을 보장했다
락은 읽기~쓰기 전체를 한 스레드만 실행하게 하고(원자성), 락을 풀 때 값을 다음 스레드에게 보이게 한다(가시성, happens-before). `synchronized`가 `ReentrantLock`보다 대체로 빨랐는데, JVM이 직접 아는 문법이라 반복문 안의 잠금·해제를 합치는 등의 최적화가 가능하기 때문으로 보인다.

### 정리: 비용과 정확성 (여러 실행을 모은 경향값)

| 방식 | 정확성 | 대략적 시간 |
|---|---|---|
| 일반 변수, JIT 켜짐 | 가끔 틀림 (숨은 버그) | 0ms |
| 일반 변수, `-Xint` | 항상 틀림 | 약 30ms |
| `volatile` | 항상 틀림 | 약 45ms |
| `synchronized` | 항상 정답 | 8~100ms |
| `ReentrantLock` | 항상 정답 | 67~210ms |

### 이 실험의 한계

- **B의 `-Xint` 적용은 기록상 증명되지 않았다.** 당시 환경 출력에 JVM 인자가 찍히지 않았다. 같은 코드가 A에서 0ms, B에서 약 30ms라는 시간 차이로 적용됐다고 판단했다.
- **A 실험의 인자를 `note latch`로 오타 냈다.** 알 수 없는 모드가 조용히 `none`으로 처리되어 결과는 같지만, 같은 원인으로 `volatile` 결과가 엉터리로 나온 적이 있다. 현재 코드는 알 수 없는 모드면 예외를 던진다.
- **시간은 경향만 본다.** 스레드 생성 비용과 JIT 예열이 섞여 있고, 같은 코드도 실행마다 크게 흔들렸다(`sync`가 한 번은 8ms, 다른 번엔 57ms).
- **JIT가 실제로 어떤 기계어를 만들었는지는 확인하지 않았다.** 기계어를 보는 도구(`hsdis`)가 폐쇄망에 없다. "한 번 읽고 한 번 쓰기"는 0ms와 정확히 1,000,000 손실이라는 간접 증거에 근거한 설명이다.
