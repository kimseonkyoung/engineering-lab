# 락을 직접 만들어 보기: 깃발 하나와 원자 명령 하나

- 날짜 / Date: 2026-10-12

## Question

1. 확인과 설정이 분리된 락(`naive`)은 `volatile`을 붙여도 정확한가?
2. 원자 명령(비교 후 교환)으로 만든 락(`spin`)은 정확한가? 표준 락보다 빠른가?
3. `ReentrantLock`의 비공정·공정 모드와 `synchronized`는 속도가 얼마나 다른가?

## Hypothesis

- `naive`: 손실이 난다. `volatile`은 깃발 값을 보이게 할 뿐, 확인(`state == 1`?)과 설정(`state = 1`) 사이의 틈은 막지 못한다.
- `spin`: 매번 정답이다. 경쟁이 짧으니 `ReentrantLock`보다 빠를 수도 있다.
- `reentrant`, `sync`: 매번 정답이다.
- `fair`: 매번 정답이지만 가장 느리다. 순서를 지키느라 매번 상대 스레드를 깨워 넘겨줘야 한다.

## Experiment

`LockImplementations.java` 하나로 다섯 가지 락을 같은 조건에서 돌린다. 두 스레드가 각자 N번 `lock()` → `balance = balance + 1` → `unlock()`을 반복하고, 기대값은 2N이다.

| 락 | 구현 |
|---|---|
| `naive` | `volatile int state`, `while (state == 1) {}` 후 `state = 1` |
| `spin` | `AtomicInteger state`, `while (!state.compareAndSet(0, 1)) {}` |
| `reentrant` | `new ReentrantLock()` (비공정) |
| `fair` | `new ReentrantLock(true)` (공정) |
| `sync` | `synchronized (MONITOR)` |

## What I learned

### 1. `volatile` 깃발은 락이 아니다
`naive`는 두 실행 모두 **한 번도 손실 0이 나오지 않았다.** `volatile`은 깃발 값을 보이게 할 뿐, 확인과 설정 사이의 틈은 그대로 둔다. 두 스레드가 동시에 0을 보고 둘 다 `lock()`을 통과한다. `balance = balance + 1`의 읽기-쓰기 틈과 똑같은 모양이 락 안에서 다시 생긴 것이다.

손실이 0.4~2.5% 수준으로 작은 건, 대부분의 시간에는 깃발이 제 역할을 하고 틈에 동시에 들어간 순간에만 손실이 나기 때문이다. **대부분 막는 락은 락이 아니다.**

### 2. 이번엔 JIT가 버그를 숨기지 못했다
`cs/race_condition`의 A 실험(락 없음, JIT 켜짐)은 20회 중 15회가 정답이었다. `naive`는 JIT가 켜져 있는데도 매번 손실이 났다. 반복문 안에 `volatile` 읽기·쓰기가 있으면 JIT가 `balance`를 레지스터에 묶어 두고 반복문을 접을 수 없기 때문이다. 1회차 손실(약 21%)이 특히 큰 건 아직 인터프리터로 느리게 돌아 틈이 길었기 때문으로 보인다.

### 3. 비교 후 교환 하나로 정확성이 확보된다
`spin`은 `compareAndSet(0, 1)`으로 확인과 설정을 원자 명령 하나(x86의 `lock cmpxchg`)로 합친다. 두 스레드가 동시에 시도해도 하드웨어가 줄을 세워 딱 하나만 성공한다. `ReentrantLock`도 같은 방식으로 `state`를 바꾼다. **원자 명령은 작은 깃발 하나에만 쓰고, 깃발을 쥔 스레드만 긴 구간을 실행하게 하는 것**이 락의 기본 구조다.

### 4. 직접 만든 `spin`이 `reentrant`보다 느렸다 (가설과 다름)
본 실행 5회 중 4회, 보조 실행 5회 중 4회에서 `reentrant`가 더 빨랐고, `spin`은 실행마다 흔들림도 컸다(139~370ms). 원인으로 보는 것:
- 기다리는 스레드가 `compareAndSet`을 계속 시도할 때마다 `state`가 담긴 캐시 줄을 독점으로 가져가려 해서, 락을 쥔 스레드의 `unlock()`을 방해한다(캐시 줄 핑퐁).
- `ReentrantLock`은 몇 번 실패하면 기다리는 스레드를 재워서 소유자를 방해하지 않는다. 비공정 모드라 방금 푼 스레드가 곧바로 다시 잡을 수 있어 캐시도 그 코어에 남는다.

이 해석은 아직 검증하지 않은 추측이다(Next question 참고).

### 5. 공정성은 비싸다
`fair`는 `reentrant`보다 6~60배 느렸다. `unlock()`할 때마다 잠든 상대 스레드를 깨워 넘겨줘야 해서, 매 반복이 운영체제 수준의 스레드 전환이 된다. 비공정 모드는 방금 푼 스레드가 다시 잡는 것을 허용해 대부분의 전환을 건너뛴다. OSTEP 28.4의 공정성과 성능이 서로 맞바꾸는 관계를 숫자로 확인했고, `ReentrantLock`의 기본값이 비공정인 이유이기도 하다.

### 6. `synchronized`가 가장 빨랐다
JVM이 직접 아는 문법이라 경쟁 시 잠깐 돌며 기다리는 적응형 회전, 연속된 잠금·해제를 합치는 최적화 등이 가능하다. 어느 최적화가 얼마나 기여했는지는 이 실험으로 확정할 수 없다.

### 한 줄 결론
**정확성은 깃발 하나를 원자적으로 바꾸느냐로 갈리고, 속도는 기다리는 방식(돌기, 재우기, 순서 지키기)으로 갈린다.**

### 내가 느낀 점
다섯 가지 락이 모두 같은 일을 하는데, 정확성은 "깃발 하나를 원자적으로 바꾸느냐" 하나로 갈렸고, 정답을 낸 네 가지 사이의 속도 차이(최대 수십 배)는 "기다리는 방식"에서 나왔다. 락을 고를 때 볼 것은 정확성이 아니라 기다리는 방식이라는 걸 알게 됐다.

### 이 실험의 한계
- 시간은 경향만 본다. 스레드 생성 비용, JIT 예열, 운영체제 스케줄링이 섞여 있고 같은 락도 실행마다 크게 흔들렸다(`fair` 856ms ~ 8.6초).
- 콘솔을 사진으로 기록해 일부 회차(본 실행 4·5회)는 줄 정렬을 숫자 크기 순서로 맞춰 읽었다.
- 실행 당시 출력 라벨이 `native`로 오타였다. 현재 코드와 기록은 `naive`로 고쳤다.
