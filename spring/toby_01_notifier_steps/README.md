## Question

토비 1장의 UserDao 리팩터링(상속 → 클래스 분리 → 인터페이스 → 생성자로 받기)을 다른 예시에 그대로 적용하면, 단계마다 **"발송 방식 하나를 추가할 때 어디를 고쳐야 하는가"**가 어떻게 달라지나?

**예시 상황.** 우리가 주문 서비스와 결제 서비스를 만들어 고객사에 판다. 주문·결제가 끝나면 고객에게 알림을 보낸다. 처음에는 문자만 있었는데, 고객사 B가 카카오톡을 원한다. 고객사 A는 계속 문자를 쓴다. 한 번에 둘 다 보내는 게 아니라 **고객사마다 하나를 골라** 쓴다.

## 설계 메모 (본인 답)

설계할 때 거친 질문 다섯 개와 그 답이다. 다른 설계에도 같은 순서를 쓴다.

| 질문 | 답 |
|---|---|
| 1. 무엇이 바뀌고 무엇이 안 바뀌나 | 안 바뀌는 것: **보낸다는 행위**, 주문·결제 처리 / 바뀌는 것: **보내는 방법** (서비스 종류도 늘어날 수 있음) |
| 2. 바뀌는 것을 누가 알아야 하나 | 주문 서비스는 방법을 몰라도 된다. "보내라"고 부르는 법만 안다. 방법을 고르는 건 **제3자** |
| 3. 어떤 덩어리가 필요한가 | `OrderService`, `PaymentService`(클래스) · `Sender`(인터페이스, 메서드 `send`) · `SmsSender`, `KakaoSender`(구현) · `Main`(제3자) |
| 4. 누가 누구를 부르나 | `Main`이 발송 객체와 서비스를 만들고 **생성자로** 넣어 준다. 서비스는 `Sender.send()`만 부르고, 뒤에 무엇이 붙었는지 모른다 |
| 5. 변경이 오면 어디를 고치나 | 아래 Hypothesis 표 |

**넣는 방법으로 생성자를 고른 이유.** 필드 직접 대입·세터·생성자 셋 중, 생성자는 발송 객체를 깜빡하면 서비스를 아예 못 만든다. 실수가 실행 중 `NullPointerException`이 아니라 컴파일 때 드러나고, 필드를 `final`로 둘 수 있다.

## Hypothesis

카카오를 추가할 때 고칠 곳 (짜기 전 예상):

| 단계 | 고칠 곳 | 새로 만들 클래스 |
|---|---|---|
| ① 상속 | 없음. 대신 카카오 코드가 서비스마다 반복 | `KakaoOrderService`, `KakaoPaymentService` |
| ② 클래스 분리 | 서비스마다 클래스 이름 + `new` + 부르는 줄 전부 | `KakaoSender` |
| ③ 인터페이스 | 서비스마다 `new` 한 줄 | `KakaoSender` (`Sender` 구현) |
| ④ 생성자로 받기 | 서비스는 0줄. `Main`에서 넣어 주는 줄만 | `KakaoSender` (`Sender` 구현) |

## Experiment

```
src/step1/Step1Main.java   상속: 추상 메서드 send를 자식이 채움
src/step2/Step2Main.java   클래스 분리: 서비스가 new SmsSender()로 직접 만들어 씀
src/step3/Step3Main.java   인터페이스: 필드 타입은 Sender, new는 아직 서비스 안
src/step4/Step4Main.java   생성자로 받기: 서비스는 Sender만 알고, main이 조립
```

- 한 프로그램에서 고객사 A(문자)와 B(카카오)를 다 보여 주려고, ②③에서는 B용으로 **고친 서비스를 복사해 따로** 두었다(`KakaoEdited...`). 실제로는 원래 파일을 고치는 것이다. 고친 줄에는 `[수정]` 주석을 달았다.
- 각 파일 맨 위 주석에 "카카오 추가 기록" 표(고친 파일, 고친 줄 수, 새 클래스 수, 반복된 코드, 단점)가 있다.
- 실제 발송 대신 콘솔 출력.

**실행 (명령줄)**

```
javac -encoding UTF-8 -d out src/step*/*.java
java -cp out step1.Step1Main      # step2.Step2Main, step3.Step3Main, step4.Step4Main
```

**Eclipse**: 패키지 `step1`~`step4`를 만들고 파일을 각각 넣은 뒤 `StepNMain`을 실행한다.

## Analysis

**고칠 곳이 서비스 밖으로 밀려난다.** ②는 서비스 안의 여러 줄, ③은 서비스 안의 한 줄(`new`), ④는 서비스 밖(`main`)이다. 밀려난 것은 **"어떤 발송 방식을 쓸지 고르는 결정"**이다.

**각 단계는 앞 단계의 약점 하나를 고친다.**

| 단계 | 얻은 것 | 남은 약점 |
|---|---|---|
| ① 상속 | 서비스를 안 고치고 바꿔 끼움 | 서비스 종류 × 발송 방식만큼 자식 클래스. 발송 코드를 서로 다른 상속 계층끼리 나눠 쓸 수 없음 (자바는 부모가 하나) |
| ② 클래스 분리 | 발송 코드가 한 곳에만 있음 (포함, has-a) | 서비스가 **클래스 이름**과 **메서드 이름**을 직접 앎 |
| ③ 인터페이스 | 메서드 이름이 `send`로 강제됨 | **구현을 고르는 `new`**가 서비스 안에 남음 |
| ④ 생성자로 받기 | 서비스는 `Sender`라는 약속 하나만 앎 | 조립을 `main`이 직접 함 → 토비 1.4 `DaoFactory`, 이후 스프링 컨테이너가 맡음 |

**①의 중복은 "부모가 달라서"만이 아니다.** 부모를 하나로 합쳐도, 발송 코드를 중간 부모로 올려도, 서비스 축과 발송 축 중 한쪽이 반복된다. 두 축이 상속 한 줄에 묶여 있기 때문이다. ④처럼 두 축을 객체로 따로 두면 클래스 수가 "서비스 수 × 방식 수"에서 "서비스 수 + 방식 수"로 준다.

**④에서 생기는 덤.** 테스트할 때 진짜 문자를 안 보내고 가짜 `Sender`를 끼울 수 있다. ①~③에서는 서비스 코드를 고치지 않고는 어렵다.

## Lessons

| 용어 | 정확한 뜻 | 이 실습에서 |
|---|---|---|
| 관심사의 분리 | 바뀌는 이유·시기가 다른 코드를 떼어 둠 | 주문·결제 처리 / 발송 방법 |
| 템플릿 메서드 | 부모가 흐름을 정하고 일부 단계를 자식이 채움 | ①의 `complete()` + 추상 `send()` |
| 구체 클래스 의존 | 코드가 특정 클래스 이름을 알고 `new`로 만듦 | ②③의 `new SmsSender()` |
| 의존관계 주입 (DI) | 쓸 객체를 밖에서 만들어 넣어 줌 | ④의 생성자 |
| 제3자 (조립하는 쪽) | 누구에게 무엇을 끼울지 정하는 곳 | `main` → 토비 `DaoFactory` → 스프링 컨테이너 |
